# Claude Code Sub-agents 演習報告

## 1. 目的

Skills 演習に続き、Claude Code の Sub-agents 機能について、実際にこのリポジトリ（`ai-sales-automation`）の未コミット差分を題材に、単一 Sub-agent の呼び出しからカスタム Sub-agent の設計・複数 Sub-agent の並行運用・結果統合までを実践した。

Skills が「再利用可能な指示・手順」の仕組みであったのに対し、Sub-agents は「独立したコンテキストと権限を持つ実行主体」を組み立てて委任する仕組みであるという違いを、実演を通じて理解することを目的とした。

## 2. 実施環境

- Claude Code
- Windows / PowerShell
- Git / GitHub
- 対象プロジェクト: `ai-sales-automation`
- 題材にした差分: `email_templates.py` の `_to_html()` への `html.escape()` 追加（未コミット）

## 3. Sub-agent とは何か（概念整理）

実践を通じて整理した理解:

- Sub-agent は、メインの会話とは別の**独立したコンテキスト**で動くタスク実行主体。`Agent` ツールで起動する。
- `subagent_type` を指定しない、または `general-purpose` を指定すると汎用エージェントが**ゼロからのコンテキスト**で起動する。会話の背景を知らないため、プロンプトには目的・前提・すでに分かっていること・具体的な作業範囲を明示的に渡す必要がある。
- `subagent_type: "fork"` の場合のみ、メインの会話コンテキストをそのまま引き継いで起動する（今回の演習では未使用。フォークは「ツール出力を自分のコンテキストに残したくない調査」向け）。
- 名前付きの Sub-agent（例: `Explore`, `code-reviewer`）は、それぞれ用途に応じて**使えるツールが制限**されている。例えば `Explore` は `Edit`/`Write` を持たず読み取り専用、`code-reviewer` は本演習で `Read, Grep, Glob, Bash` に制限したカスタム定義。
- Sub-agent はバックグラウンドで非同期に実行され、完了すると `task-notification` としてメインの会話に結果が届く。起動直後の結果を先読み・推測してはいけない（実際に完了通知が来るまで内容は分からない）。

## 4. 単一 Sub-agent の呼び出し実践: `code-reviewer`

まず最も単純な形として、`code-reviewer` という名前付き Sub-agent 1体だけを使い、`email_templates.py` の差分をレビューさせた。

ポイント:

- 呼び出し側（メインClaude）がプロンプトに、対象の差分の取得方法（`git diff`）、リポジトリ固有の重要な不変条件（`outlook_draft.py` は `mail.Save()` のみで `mail.Send()` は呼ばない）、確認してほしい観点（バグ・可読性・保守性・セキュリティ）を具体的に書いて委任した。
- Sub-agent は独自に `git diff` を実行し、`html.escape()` 追加を「HTMLインジェクション対策として妥当なセキュリティ改善」と評価し、重要度つきで報告した。
- `tools` が `Read, Grep, Glob, Bash` に限定されているため、レビューのみでファイル変更ができない構成になっていることを確認した。

## 5. カスタム Sub-agent の定義: `.claude/agents/code-reviewer.md`

このプロジェクト専用の Sub-agent を、frontmatter 付き Markdown で定義した。

```yaml
---
name: code-reviewer
description: コードレビュー専門のサブエージェント。バグ・可読性・保守性・セキュリティの観点で差分やファイルをレビューし、重要度つきで問題点を報告する。「レビューして」「コードを確認して」といった依頼で使う。
tools: Read, Grep, Glob, Bash
model: sonnet
skills:
  - summarize-changes
---
```

学んだ frontmatter 項目:

- `description`: メインClaudeがこの Sub-agent を**自動選択**する際の判断材料になる。呼び出しトリガーの例文を含めると精度が上がる。
- `tools`: この Sub-agent に許可するツールのホワイトリスト。役割に対して過不足がないか設計する必要がある。
- `model`: タスクの推論負荷に応じたモデル選択（本演習では `sonnet` を採用）。
- `skills`: 起動時に**プリロードするSkill**を指定できる。`summarize-changes` を指定すると、その Skill の内容が起動時からコンテキストに注入され、Sub-agent が最初から利用可能になる。

### `skills` プリロードの追加

既存の役割・`tools`・`model`・本文を一切変えずに `skills: - summarize-changes` だけを frontmatter に追加する変更を行った。Skill と Sub-agent は独立した仕組みだが、`skills:` フィールドで組み合わせられることを確認した。

### `description` / `tools` / `model` の妥当性レビュー

作成した Sub-agent 定義そのものを見直す演習も行った。

- `description` と `model`（`sonnet`）は現在の役割に対して適切と判断した。
- `tools` の `Bash` は、注意書きの「ファイルは一切変更しないこと」という設計意図に対して**権限が広すぎる**という指摘に至った。Bash は本質的に汎用シェルであり、読み取り専用の `git diff` 取得以外の操作（`git add`, `rm` など）も実行可能なため、最小権限の観点では `Bash(git diff:*)` のような読み取り専用コマンドへの限定が望ましいという結論になった（今回は指摘のみで変更は行っていない）。

## 6. 複数 Sub-agent による並行分析（マルチエージェント構成）

同じ `email_templates.py` の差分に対して、役割を分担した複数 Sub-agent を**並行起動**し、メインClaudeが結果を統合する構成を2段階で実践した。

### 6-1. 2エージェント構成: `Explore` + `code-reviewer`

| Sub-agent | 役割 | 使用ツール |
|---|---|---|
| `Explore` | 変更の影響範囲調査（呼び出しチェーン・副作用の追跡）。ファイル変更なし | 読み取り専用ツール一式 |
| `code-reviewer` | バグ・可読性・保守性・セキュリティ観点のレビュー。ファイル変更なし | `Read, Grep, Glob, Bash` |

2体を**同一メッセージ内で並行起動**し、それぞれ独立に完了通知が届いた時点で、メインClaudeが両者の結果を突き合わせて「問題なし」と最終判断した。

`Explore` は `main.py` → `render()` → `_to_html()` → `outlook_draft.create_draft()` という呼び出しチェーンと、`config.USE_HTML` フラグの分岐、プレースホルダー値（`課題メモ` が Claude API による自動生成テキストであること）まで具体的に特定した。`code-reviewer` は同じ差分をセキュリティ・品質面から評価し、両者の結論が一致した。

### 6-2. 3エージェント構成: `Explore` + `code-reviewer` + `general-purpose`

さらに役割を1つ追加し、`general-purpose` エージェントに「前の2つの分析結果を前提として、修正が必要な場合の修正案だけを作る」という役割を与えた。

ポイント:

- `general-purpose` は `fork` と異なりゼロからのコンテキストで起動するため、プロンプトに `Explore` と `code-reviewer` の分析結果全文を要約して渡し、「自分で再調査する必要はない」と明記した。これにより、同じ調査を重複して行わせずに済んだ。
- このとき、**同じ差分に対する `Explore`/`code-reviewer` の分析がすでに会話内に存在する**ことに気づき、重複起動を避けて既存結果を再利用し、新規に追加した役割（修正案作成）の Sub-agent だけを起動した。これは Sub-agent 運用における「同じ調査をエージェントに何度もやらせない」という効率面の学びになった。
- `general-purpose` は指摘された低優先度の所感2点について「対応不要」と判断理由つきで回答し、あくまで参考コード例に留めて実ファイルは変更しなかった。

### メインClaudeによる統合判断

複数 Sub-agent の結果を受け取ったメインClaude自身は調査・レビューを行わず、**各エージェントの結論を比較・要約し、最終的な意思決定（問題なし / 修正推奨 / 要修正）だけを行う**という役割分担になることを確認した。今回はいずれの回でも「問題なし」という一致した結論に至った。

---

## 7. 学んだこと（まとめ）

- Sub-agent は「独立したコンテキスト」「制限されたツール権限」「非同期実行」という3つの特性を持つ、Skill とは異なるレベルの委任の仕組みである。
- `subagent_type` によって、コンテキストを引き継ぐか（`fork`）、ゼロから始めるか（それ以外）が変わり、プロンプトの書き方（背景説明の要不要）が根本的に変わる。
- カスタム Sub-agent の `tools` は、役割に対して最小限になっているかを都度見直す価値がある（本演習では `Bash` の権限範囲が見直し候補として浮上した）。
- 複数 Sub-agent を役割分担させ並行起動することで、「調査」「レビュー」「修正案作成」を独立した視点として突き合わせられる。ただし同じ対象への重複分析は避け、既存結果を再利用する判断も重要。
- 最終的な意思決定（問題なし/修正推奨/要修正）はメインClaude側の役割であり、Sub-agentはあくまで専門特化した分析・提案を返す立場に留める設計が機能した。
